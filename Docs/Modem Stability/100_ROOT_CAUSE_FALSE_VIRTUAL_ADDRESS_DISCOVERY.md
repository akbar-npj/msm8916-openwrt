# Engineering Report 100: Root Cause Discovery - False Virtual Address Base (0xd2312000 vs 0xc3e0f000)

## 1. Executive Summary

During our deep analysis of the crash coredumps (`modem_coredump_p28r.elf` and `modem_coredump_p29.elf`), a critical root cause was discovered that explains why all previous vtable injections and memory copies failed:

> [!CAUTION]
> **The virtual address base `0xd2312000` used in Patches 23–29 was completely fictitious.**
> It originated from a decompilation label (`SUB_d2312000`) in a Ghidra project and has **zero existence** in the QDSP6 MMU page tables.
> The genuine virtual address of Segment 26 (`modem.b26`) is **`0xc3e0f000`**.

Because `0xd2312000` is completely unmapped in the QDSP6 virtual address space:
- Every device pointer (`0xd23fa000`) written to the 17 LTE band slots in `card_ptr + 0x424` pointed to **unmapped / non-existent memory**.
- Every vtable entry (`0xd23fa040`), method address (`0xd23fa080`), sub-device (`0xd23fa0c0`), and stub (`0xd23fa180`) was an invalid pointer.
- Whenever Layer 1 attempted to access the band device or call a method on it, QDSP6 suffered an immediate TLB miss / page fault (`SSR = 0x0000000a`).

## 2. Definitive Proof from ELF Header and Devcoredump

### 2.1 ELF Program Header in `modem.mdt`
We parsed the program headers of `modem.mdt` directly:
```
Segment 26 Program Header:
  p_type   : 0x1 (PT_LOAD)
  p_flags  : 0x8000007 (QCOM_MDT_RELOCATABLE | PF_R | PF_W | PF_X)
  p_vaddr  : 0xc3e0f000  <-- TRUE VIRTUAL ADDRESS
  p_paddr  : 0xc3e0f000
  p_filesz : 0x00100000 (1,048,576 bytes = modem.b26)
  p_memsz  : 0x00100000
```

### 2.2 Devcoredump Memory Map (`modem_coredump_p29.elf`)
The coredump generated by the Linux kernel `remoteproc` driver dumps every mapped QDSP6 segment:
```
Total Segments: 22
...
Seg 18: VA 0xc3486000..0xc3dea000 (modem.b23)
Seg 19: VA 0xc3deb000..0xc3e0e24c (modem.b25)
Seg 20: VA 0xc3e0f000..0xc3f0f000 (modem.b26, 1MB)  <-- Mapped at 0xc3e0f000!
Seg 21: VA 0xc3f10000..0xc5500000 (heap / bss)
```
**`0xd0000000..0xdfffffff` is NOT mapped anywhere in the running modem.**

## 4. Remediation Plan (Patch 30)

1. Change `VA_BASE` in the patch tool from `0xd2312000` to **`0xc3e0f000`**.
2. Update all injected absolute pointers (`DEV_VA`, `VTBL_VA`, `METH_VA`, `PRX_VA`, `DRX_VA`, `DVT_VA`, `RET0_VA`, `RET1_VA`) and the helper immediate load to use the genuine `0xc3ef7...` addresses.
3. Keep the `card_init` success bypass at `0x260b8` (`{ r0 = #1 }`) and the hook at `0x260d4` (`{ jump 0xe8200 }`).
4. Re-hash Segment 26, rebuild `modem.mdt`, deploy, and cold reboot.
