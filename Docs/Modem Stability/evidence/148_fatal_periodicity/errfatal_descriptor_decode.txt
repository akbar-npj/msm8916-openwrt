## Why this matters

`reference_err_fatal_file_line_decode.md` recorded that the descriptor -> file/line link
"is NOT decoded" and that descriptors "read as high-entropy obfuscated data even in rodata".
**Both are now shown to be wrong for this descriptor family.** The runtime copy in a modem
coredump is plaintext and structurally exact.

## The layout (verified)

Formatter is at `0xc08794e0`; it reads:
    line     = zxth(memw(r18 + 0x00))     # u16 at +0x00
    filename = (char *)(r18 + 0x14)       # inline NUL-terminated at +0x14

Observed bytes at file offset 0x03524f54 - 0x14 = 0x03524f40 (VA 0x89db1290):

    +0x00  86 01 00 00   u16 line = 0x0186 = 390
    +0x02  00 00         pad
    +0x04  62 be 78 c7   u32 A   (runtime-varying, see below)
    +0x08  12 8c 12 01   u32 B   (runtime-varying, see below)
    +0x0c  00 00 00 00   0
    +0x10  00 00 00 00   0
    +0x14  "lte_ml1_common_timer.c\0"

That is an EXACT match to what the formatter reads. The descriptor is the one that produced
the observed kernel message `fatal error received: lte_ml1_common_timer.c:390:`.

## It is a STATIC object, but its payload is runtime state

The descriptor sits at the SAME file offset (0x03524f54) in every coredump => same VA
0x89db1290 => it is a compile-time object, not a stack copy. Yet two of its words change
between dumps:

    dump (uptime s)     A           B
    up919.52            0xb7bb76cf  0x01128bfc
    up1000.86           0xb7bb76cf  0x01128bfc     <- same as up919.52 (81 s apart)
    up1822.52           0xbffa3d53  0x01128c07
    up2723.69           0xc778be62  0x01128c12
    up3629.79           0xce3f7ed6  0x01128c1d

* B increases monotonically: 0x01128bfc -> 0x01128c07 -> 0x01128c12 -> 0x01128c1d
  (delta 0x0b = 11 per fatal period). Over up919.52 -> up3629.79 (delta 2710.27 s) B rises 33,
  i.e. **one count per ~82.1 s**. B is NOT a plain tick count (it would scale 1:1 with uptime).
  Candidate: a counter of some event with a ~82 s period, captured into the descriptor.
* A also varies, increasing with uptime but with a decreasing increment
  (0x083EC684, 0x077E810F, 0x06C6C074). Not yet interpreted; it does not look like an address
  (the modem's code lives at 0xc0.., and 0xb7bb76cf is below that).

## RESOLVED 2026-09-20: the coredump <-> ELF address mapping, and what 0x89db1290 actually is

### The mapping: `dump_va = elf_va - 0x39800000`

The coredump uses **physical** addresses; the ELF uses **virtual**. The delta is exactly
0x39800000, verified on four independent segment bases AND on the string pool itself:

| ELF VA | coredump VA | evidence |
| :--- | :--- | :--- |
| 0xc0000000 | 0x86800000 | segment base |
| 0xc0287000 | 0x86a87000 | segment base |
| 0xc1500000 | 0x87d00000 | segment base |
| 0xc175b2b8 (`lte_ml1_common_timer.c` literal) | 0x87f5b2b8 | same content at the same in-segment offset 0x25b2b8 |

So descriptor dump-VA 0x89db1290 -> **ELF VA 0xC35B1290**, which lands in the ELF PT_LOAD at
`0xc2070000` with **`filesz = 0`, `memsz = 0x1b98840`** — i.e. **BSS**. That is exactly why a
byte search of the ELF for the descriptor found nothing: the object has no file content.

### What 0xC35B1290 is: the single global "last fatal" record

Searching `modem.asm` for the **ELF** VA (not the dump VA — that was the earlier mistake) gives
three references, and all of them are inside the ERR_FATAL machinery:

```
c0878fec:  r3  = memw(##0xc35b1290)      # read the record
c08793d0:  r19 = memw(##0xc35b1290)      # read the record
c0879504:  r18 = ##-0x3ca4ed70           # r18 = 0xC35B1290  <-- the formatter's own r18
```

`c0879504` is immediately adjacent to the formatter at `0xc08794e0` that the earlier note
identified as reading `line` at `+0x00` and the filename at `+0x14` via `r18`. And
`c0878fdc: r1 = ##0xc35b12a4` is `0xC35B1290 + 0x14` — the inline filename.

**Conclusion: 0xC35B1290 is not a per-assert descriptor. It is the one global record that the
ERR_FATAL path fills with the *most recent* fatal's {line, A, B, filename}, then formats.** So:

* the decoded line/filename tell us only what we already know from `dmesg` — the last fatal was
  `lte_ml1_common_timer.c:390`;
* the two payload words A and B are **captured at the fatal**, and B increments by exactly 0x0b
  (11) per fatal period, i.e. one count per ~82.15 s. That is a real, unexplained quantity — it
  is the only lead the descriptor gives.

### Where the assert site actually is

The `lte_ml1_common_timer.c` **string literals live at ELF VA 0xc175b2a4** (10 consecutive
copies, stride 0x18), which is in the ELF segment at **`0xc1500000` (filesz 0x73ace0)**.
`scratch/firmware/modem.asm` stops at **0xc1404e0c**, so that segment — and therefore
`lte_ml1_common_timer.c`'s own code and rodata — **is not disassembled**. That is the concrete
next step for the RE: disassemble `0xc1500000` and look for the ERR_FATAL call that passes this
file/line.

Also checked and negative: none of the four `rN = #0x186` sites in `modem.asm`
(`c02c3930`, `c04b01bc`, `c0b3e0e8`, `c0cb0b64`) is the assert — they are 25-41 instructions
away from the nearest `call 0xc0879150` and are arithmetic/structure-init uses.

## Still open

* The meaning of A and B. B is the promising one (11 per fatal period, ~82.15 s per count).
* The assert site, blocked on disassembling the `0xc1500000` segment.


## Operational note — coredump reading is a DISK HAZARD

`/sys/class/devcoredump/` exposes a SINGLE device (`devcd4`). Repeated reads return *changing*
data (a live dump), so a naive polling loop writes a fresh 85 MB file each time. The watch
used here wrote **122 dumps = 9.6 GB in ~45 min** before being stopped. Always bound the
number of captures, and prune. One dump per fatal era is enough.
