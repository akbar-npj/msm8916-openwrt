3. THE CRASH SITE -- ANATOMY  (this is the attribution the patch rests on)
--------------------------------------------------------------------------------
Crash-log facts (evidence/227_ap_side_stock_restore/02_natural_fatal_crash_log.txt):
  file/line : lte_ml1_common_timer.c:390   REX task: tmr_slave3
  LR = 0xc0879164 (inside ERR_FATAL 0xc0879150), SP = 0x8ad52160
  stack @0x8ad52174 = 0xc02d7bd0   <- the callback's entry address
  stack @0x8ad5217c = 0xc02d7d8c   <- return address of the ERR_FATAL call

=> the fatal ERR_FATAL call is the 12-byte packet at ELF VA 0xc02d7d80, inside
   the function at 0xc02d7bd0.

Corroboration from the coredump corpus (scratch/coredump_live/): the ERR_FATAL
record at ELF VA 0xC35B1280 has +0x10 = 0x0186 = 390 in *every* dump
(fatal_fields.py), and the callback address 0xc02d7bd0 is stored as a *native*
ELF VA in modem memory (191 occurrences).

The function 0xc02d7bd0 is NOT in modem_full_decompiled.c because it is only
ever reached as a *registered callback pointer*: FUN_c02d7b80 @0xc02d7b80 does
  thunk_FUN_c0b61cc0(param_1, puVar1, &UNK_c02d7bd0, param_1);
i.e. a REX timer registration.  Hence the decompiler marked it UNK_ and never
emitted it -- which is why this site was previously unattributed.

Structure of 0xc02d7bd0 (verified by disassembly, scratch/hmu05_stock_elf/
disasm_b16.txt lines 81333-81570):
    call 0xc02d1140 ; r16 = r0 ; allocframe(#0xb0)
    r1 = memub(r16+#0x38)            ; a STATE byte of the 0x168-byte object
    r2 = memw(gp+#0xba64)            ; jump table
    r2 = memw(r2+r1<<#0x2) ; jumpr r2 ; SWITCH(state)
  ... case bodies at 7bf0, 7c60, 7cac, 7cd4, 7cfc, 7d20 ... each does
      call 0xc02871ac(...) ; call 0xc0287198(...,state) ; store state
      p0 = cmp.eq(r0,#0x0) ; if (p0) jump:t 0xc02d7df8   ; r0==0 -> CLEAN EXIT
      call 0xc0879150  (ERR_FATAL)                        ; r0!=0 -> DIE
  0xc02d7df8 is the function's ONLY epilogue: r17:16 = memd(r29+#0xa8); dealloc_return

The object is the per-index ML1 "UE mobility" object: FUN_c02d7e20 allocates it
with FUN_c02d11a0(index, 0x168, s_lte_ml1_common_uemob_c_c1a86250, 0x14d) and
keeps it in DAT_c312b9e4[index]; FUN_c02d7b80 reads memb(obj+0x38)==0x13.

=> The crash is NOT the MCPM supervisor.  It is the FAILURE PATH of a resource
   check inside a registered ML1 timer callback: a call (0xc0287198) returned
   non-zero and the code asserted.  There are TEN such ERR_FATAL sites in this
   one function:
     0xc02d7c18 0xc02d7c4c 0xc02d7c90 0xc02d7cb8 0xc02d7ce0
     0xc02d7d14 0xc02d7d48 0xc02d7d80 0xc02d7dd8 0xc02d7de4

This CONFIRMS evidence 10 §6's tentative conclusion (the fatal is the assert at
the reported site, not the MCPM supervisor) and makes the ranked firmware
interventions of 900S_CRASH_LPR_FRAMEWORK_RE.md §8 (patch 0xc0ce81d4, raise the
400 threshold, MCVS bypass) INAPPLICABLE -- they all target the MCPM gate, which

4. WHY THE PREVIOUS (Doc 229) 3-SITE PATCH FAILED -- AND WHY THIS ONE DIFFERS
--------------------------------------------------------------------------------
Doc 229 §5 replaced the same 12-byte fatal packets with three nops.  A nop lets
execution FALL THROUGH to the next packet, which was written on the assumption
that the ERR_FATAL never returns (the very next thing after 7c18 is the *next
case body* at 7c24).  That is a broken continuation, and it is the most likely
cause of the "early fatal" and the relocation to a2_task.c:1184/:3179.

This patch does NOT use nops.  Each of the 10 sites becomes
    jump 0xc02d7df8  ; nop ; nop
i.e. an unconditional jump to the function's real epilogue, preserving the frame
teardown and never falling into the neighbouring case.  The case body's work
(the two calls + the store) still executes before the exit; only the DIE is
replaced by a RETURN.

10. ROOT-CAUSE PROGRESS -- THE FAILING CALL IS AN F3 LOG-EMIT, NOT A DATA-PATH CALL
--------------------------------------------------------------------------------
(This narrows the "not a root fix" gap.  It is a hypothesis with a strong static
basis, NOT yet a verified mechanism.)

The failing call is the thunk at `0xc0287198` -> `r1 = #0x18 ; jump 0xc0b62f10`.
The *other* call in every case body, `0xc02871ac` -> `jump 0xc0b63880`, is
**an F3 log-record initialiser**, and it proves what the pair is for:

  c0b63880(r0=rec, r1=line, r2=(line<<16)|code):
      if (rec == 0) jump 0xc0b638d4          ; NULL -> 0xc0b63b40 (alloc path)
      r3 = ##0x31415926 ; memd(rec+0x8)=0 ; memd(rec+0x0)=0
      memw(rec+0x0) = r2                     ; rec+0x00 = the packed descriptor
      r4 = memw(0xc2fe7220)                  ; the subsystem magic
      if (r4 != 0x31415926) skip
          r1 = memub( memw(0xc2fe722c) + memw(0xc2fe7234)*16 )   ; per-site byte
      memb(rec+0x7)=0 ; memb(rec+0x8)=0x7f ; memb(rec+0xa)=0
      memb(rec+0x6)=r1 ; memb(rec+0x9)=0
      dealloc_return

  i.e. it fills a 12-byte log record: +0 = (line<<16)|code, +6 = the per-site
  enable/level byte from a 16-byte-stride table at 0xc2fe722c, +8 = 0x7f.

`0xc0b62f10(rec, index=0x18)` then: validates the same magic at `0xc2fe7220`,
rejects `rec == NULL` and `index <= 0xf`, **atomically increments a global
counter at `0xc3c0e83c`** (`memw_locked`), walks the same 16-byte-stride table,
does an indirect `callr` through `memw(0xc2fe7224)`, and **returns a status that
the caller tests against 0**.  Caller counts in b16: `0xc02871ac` **259**,
`0xc0287198` **77**.

=> **The fatal is "the modem failed to EMIT an F3 log record, and the ML1 timer
   callback asserts on that failure"** — reported against
   `lte_ml1_common_timer.c:390`, in REX task `tmr_slave3`.

WHY THIS IS THE RIGHT SHAPE OF ANSWER: it is a *diagnostic-pipeline* failure, not
a data-path or RF failure.  That is consistent with (a) the fatal needing no
bearer and no AP data path (Doc 229 §2), (b) the fault being LTE-stack-gated
(`offline` suppresses it — no ML1 activity, so no log traffic), and (c) the
OpenWrt-vs-Android rate differential (25x): **Android runs a DIAG consumer; the
OpenWrt and pmOS ports do not.**

TWO THINGS IT DOES NOT EXPLAIN YET, stated so they are not glossed over:
  1. **The absolute-AON anchor (§2).**  A log ring filling would be *modem-uptime*
     based, and §2 shows it is not.  The remaining candidate that is both
     absolute-time-based and able to fail an emit is a **timestamp field**: if the
     record carries a free-running counter that wraps, an emit-time validation
     could reject it at the wrap.  `P = 903.6752001 s` implies a 32-bit counter at
     **4,752,349.94 Hz** — not a standard msm8916 clock (XO/4 = 4.8 MHz gives
     894.785 s, 1.0 % away; 19.2e6/4.04 gives 903.651 s, 26 ppm away).  **Not
     resolved.**
  2. Whether the emit fails because of a *backlog* (nothing draining DIAG) or
     because of a *validation* (timestamp/wrap).  The discriminator is cheap and
     safe: a backlog would fail **from boot**, a validation fails **only at the
     wrap** — and we observe a clean 902.97 s of successful operation first.
     ⇒ **the validation/wrap reading is favoured, the backlog reading is
     disfavoured.**  (The corpus capture that spans a fatal WAS draining DIAG and
     still fataled, which independently disfavours "backlog".)

NEXT TEST (designed, not run): on a **stock** firmware soak, bind a DIAG drain for
the whole epoch.  If the fatal still fires at the beat, the backlog reading is
dead and the emit failure is a *symptom*.  If the fatal stops, the log pipeline
IS the mechanism and the fix is AP-side (drain DIAG).  This is a one-line
prediction with a falsifiable outcome and it does not need the baseband patch.
