WHY THIS FILE EXISTS
--------------------
Doc 170 s8.13 turned the remoteproc coredump capture OFF to test whether a step
INSIDE the SSR recovery is implicated in the AP hang.  A second draft of s8.13
then argued, from the CALL GRAPH, that this could NOT remove "port failed halt"
(because q6v5_mba_reclaim() is also called by q6v5_stop():1672, which rproc_stop()
runs unconditionally).  This file is the measurement that RETRACTED that argument.

WHY MY CORRECTION WAS WRONG (the transferable lesson)
-----------------------------------------------------
q6v5proc_halt_axi_port() (qcom_q6v5_mss.c:961-975) opens with

        /* Check if we're already idle */
        ret = regmap_read(halt_map, offset + AXI_IDLE_REG, &val);
        if (!ret && val)
                return;                 /* EARLY RETURN -- prints nothing */

and only reaches dev_err(..., "port failed halt") if the halt FAILS.

  STOP path: the modem has just crashed and been reset => the AXI port is ALREADY
             IDLE => early return => SILENT.
  DUMP path: q6v5_reload_mba() has JUST re-loaded and re-started the MBA => the
             reclaim halts the AXI port of a LIVE MODEM => times out => the message.

  => "port failed halt" means "the reclaim ran against a LIVE modem".
  => A CALL SITE BEING REACHED IS NOT EVIDENCE THAT ITS ERROR BRANCH EXECUTES.

WHAT STILL SURVIVES (so the prediction is not over-read)
--------------------------------------------------------
The restart's OWN q6v5_mba_load() still runs, and its untraced tail is still there:
trace 23 -> MBA booted = 39.2 ms, which is q6v5_rmb_mba_wait() -- the call Doc 165
identified as 86.2 % of the 43.968 ms window.  A same-duration window of the same
kind therefore REMAINS, merely relocated from
"port failed halt"->"MBA booted"  to  "stopped remote processor"->"MBA booted".
q6v5_rmb_mba_wait() is BOUNDED (msleep(1) + time_after, 5000 ms -> -ETIMEDOUT ->
"MBA boot timed out"), so it cannot hang forever -- but if the AP hang lives inside
IT, this experiment will not remove the hang.
