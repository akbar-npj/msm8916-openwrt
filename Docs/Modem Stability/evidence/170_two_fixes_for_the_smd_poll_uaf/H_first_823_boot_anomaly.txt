3. THE SHAPE OF IT, AND WHY IT IS NOT THE KNOWN list_del UAF
---------------------------------------------------------------------------
  t=72.95   a GRACEFUL rproc_stop() is requested by something
  t=72.95   sysmon_stop -> blocking_notifier_call_chain -> bam_dmux schedules its
            teardown work
  t=73.45   the ssctl wait times out (500 ms) -- the graceful handshake failed
  t=73.45-  the bam_dmux teardown runs to completion: T0..T9 ALL PRESENT, with no
  t=73.55   list_del corruption.  This is the same "complete teardown" the
            natural-fatal Question B run showed.
  t=73.93   a runtime RESUME is attempted and the modem does not ACK the
            power-collapse vote within 250 ms
  t=73.93   console stops -> AP hang -> watchdog reboot

  It is NOT the Doc 169/170 UAF: that one reports `list_del corruption` and kills
  the AP in the poller's poll_freewait().  Here the teardown is clean and the
  hang is in the modem power-collapse/resume handshake afterwards.

  It IS in the same family as Doc 159 (the AP hangs on a natural fatal-triggered
  SSR) and Doc 166's second, earlier hang site -- but with no `fatal error
  received` anywhere, so it was not a modem fatal.

4. WHAT IS AND IS NOT RULED OUT
---------------------------------------------------------------------------
NOT the watchers.  Nothing under /overlay writes remoteproc state.  Grepped on the
device with its own grep (the host-side `rg` is absent there, so a host `rg` over
ssh returns nothing -- do not read that as "not found"):

    /overlay/coredump_watch.sh:52,56,57   reads .../remoteproc0/coredump only
    /overlay/ssr_ledger.sh:59             reads the bam-dmux rx_telemetry only
    /overlay/q6trace_soak.sh:61           reads the bam-dmux rx_telemetry only

NOT reproducible so far.  The very next boot -- also running 823 -- shows NONE of
these messages and was still healthy at uptime 173 s, well past the 73.93 s hang
point:

    dmesg | grep -nE "ssctl|pc-ack|SSR teardown|fatal error|list_del"   -> empty
    uptime 173.03 s, rproc=running, wwan0 UP with a route, ping 4/4

  So the observation is 1 boot out of 2 with 823.

823 IS NOT EXCLUDED, and the mechanism has not been established either way.  A
hand-waved "823 cannot call rproc_shutdown" is an argument from the patch's text,
not a measurement, and this project has already been burned once this round by
inferring a mechanism from a pattern (see the memory entry on Doc 166 section 5.4).
The clean discriminator is a controlled comparison: boot with the unpatched module
(bash scratch/deploy823.sh --revert) and check whether the same
ssctl -> teardown -> pc-ack sequence appears.  That has NOT been run.

---------------------------------------------------------------------------
5. TWO CONFOUNDERS PRESENT ON THIS DEVICE, RECORDED FOR WHOEVER RUNS THAT TEST
---------------------------------------------------------------------------
(a) A device-specific script loops every 10 s and drives the modem through
    ModemManager:  /usr/sbin/qcom-carrier-autocfg (563 lines, `while ... sleep 10`).
    It calls, among others,
        mmcli -m M --set-power-state-low / --set-power-state-on / -e   (reset_baseband_cache)
        mmcli -m M --simple-disconnect, --delete-bearer, --3gpp-set-initial-eps-bearer-settings
    and it can `reboot` the device itself (lines ~529 and ~537) when an MBN change
    is detected.  A 10 s loop that power-cycles the modem through QMI is a live
    confounder for ANY modem-state experiment on this image and had not been
    catalogued before.
(b) The device was carrying a heavy instrumentation load of my own: 5 instances of
    q6trace_soak.sh, 3 of beacon.sh, ssr_ledger.sh, coredump_watch.sh,
    ModemManager, mmcli -M, collectd, qcom-time-daemon.  Under the Doc 170 section 8
    load hypothesis that load makes the UAF MORE likely, not less -- and it still
    did not reproduce in the two controls.
