HYPOTHESIS
----------
The AP hang happens inside the SSR recovery, and the COREDUMP CAPTURE is a step of
that recovery.  Removing it removes the hang.

       CAREFUL -- there are TWO different sysfs locations and the corpus does not
       distinguish them:
         /sys/class/devcoredump/devcdN/            per-device attrs are ONLY "data"
                                                   (corpus note "no per-device disabled"

                                                   (THIS is the one we write)
         /sys/class/devcoredump/disabled           CLASS-level, write-once GLOBAL
                                                   lockdown -- kills every future dump.
                                                   NEVER WRITE IT.
       The remoteproc attribute selects whether a dump is PRODUCED AT ALL; the class-level
       one is a global kill switch.  They are not the same thing.

WHY THE SKIPPED STEP MATTERS
----------------------------
* qcom_q6v5_dump_segment() is the SECOND caller of q6v5_mba_load() (Doc 165) --
  a whole extra MBA power-up/handshake per fatal, mid-recovery.
* Doc 165 measured the 85 398 475 B synchronous copy at 1.064 s ON this path.
* It writes 85 MB per fatal to /overlay -- 18 dumps = 1.5 GB of a 3.2 GB partition.

WHAT THIS DOES *NOT* DO -- corrected after reading the callers (first draft overclaimed)
-------------------------------------------------------------------------------------
It does NOT remove Doc 159's hang site.

  q6v5_mba_reclaim() has THREE callers:
      qcom_q6v5_mss.c:1616   the coredump's reclaim      <- removed by this experiment
      qcom_q6v5_mss.c:1657   q6v5_mpss_load error path   <- not on the recovery path
      qcom_q6v5_mss.c:1672   q6v5_stop()                 <- rproc_stop() runs this
                                                          UNCONDITIONALLY
  q6v5_mba_reclaim() is what calls q6v5proc_halt_axi_port() (:1282-1286), and THAT
  is where "port failed halt" is emitted (:974).

  => "port failed halt" is produced by the STOP path, not the coredump path, so the
     43-47 ms window Doc 159 located the hang in is STILL PRESENT with the dump off.

WHAT THE EXPERIMENT THEREFORE TESTS (the weaker, accurate claim)
----------------------------------------------------------------
Not "the hang site is removed", but "the recovery does ~1 s less work and one fewer
MBA power-cycle/reclaim in the middle of a 44 ms window".  That is still a real
hypothesis -- extra MBA load + a second reclaim are exactly the kind of work that can
wedge a narrow handshake -- but it is weaker, and the pre-registration is written
against the weaker claim.

DEPLOYED (survives reboot, trivially reversible)
------------------------------------------------
/etc/rc.local:
    if [ -x /overlay/coredump_watch.sh ] && [ -f /overlay/coredump_ENABLE ]; then
            ... start the watcher (it re-arms the attribute every 2 s) ...
    else
            echo disabled > /sys/class/remoteproc/remoteproc0/coredump 2>/dev/null
            /usr/bin/logger -t coredump-watch "coredump capture DISABLED (Doc 170 s8.13)"
    fi

Verified at start:
    cat /sys/class/remoteproc/remoteproc0/coredump  -> disabled
    ps | grep -c coredump_watch                     -> 0
    sh -n /etc/rc.local                             -> SYNTAX OK
    grep -c coredump_ENABLE /etc/rc.local           -> 3
    /overlay/coredump_ENABLE                        -> absent

RE-ENABLE:  touch /overlay/coredump_ENABLE   (then reboot, or just start the watcher --
            it re-arms the attribute to "enabled" within 2 s)

PRE-REGISTRATION (written before the run)
-----------------------------------------
Prediction : if the coredump path is the hang, the AP reboot rate falls to ZERO.
Bar        : 0 AP reboots across the next 20 fatals (~5 h at the ~902 s idle timer).
Why n=20   : the pre-823 rate was of order 1 reboot per 1-3 SSRs, so 20 clean fatals is
             decisive; if the true post-823 rate were as low as 1 in 4, 20 fatals still
             gives ~99.7 % chance of seeing at least one.
Control    : the pre-intervention series of §8.11 -- explicitly WEAK (confounded by
             manual activity, boot loops, and pre-823).  This is a before/after, not an
             A/B; an A/B (off -> on -> off) is the stronger design if device time allows.
Falsified by: any reboot in the window, OR a dmesg_roll tail showing the recovery had
             already passed the coredump step.
Cost       : no coredump is captured during the window, so a fatal in this period cannot
             be decoded via its ERR_FATAL descriptor (Doc 163).  The fatal SIGNATURE still
             lands in dmesg_roll and the ledger still records the teardown stages, so the
             loss is bounded.
