===============================================================================
3. WHAT THE ADDED DATA CHANGED, AND WHAT IT DID NOT
===============================================================================

* **The MAX did NOT move.**  3.160 ms in the n=204 snapshot (uptime 3883 s) and
  3.160 ms in the n=911 frozen copy (uptime 7142 s) -- 707 further handshakes
  produced no new maximum.  A saturated extreme is a stable statistic; this is
  the strongest single sign that the capture is one homogeneous regime.
* **The p50 DID move**: 1.891 -> 0.699 ms.  This is NOT a drift -- the wakeup
  rate rose from 3.15/min to 7.67/min (the boot-2 ping loop is active later in
  the boot), and a different traffic mix produces a different SHAPE.  **Report
  the maximum and the tail counts; do not compare p50 across windows with
  different traffic.**  Same lesson as the MCPM cadence (Doc 174 s9).
* **The tail counts are all zero at every threshold down to 5 ms.**  That is a
  stronger statement than "no timeout": the distribution has no visible tail at
  all in 911 samples.

===============================================================================
4. HONEST LIMITS
===============================================================================

1. **ONE boot.**  n = 911 is deep but it is a single boot's worth of one device.
   The bar was a sample-size bar, not a boot-count bar, so the bar is met; a
   second boot would test boot-to-boot reproducibility, which is NOT claimed here.
2. **Android CANNOT measure the post-fatal regime.**  Android has 0 fatals, so
   this control is silent on exactly the regime where OpenWrt fails.  It bounds
   the HEALTHY cost of a handshake; it does not prove the 250 ms value is wrong.
   The A/B (Task #98) is what tests that, and it is pre-registered as a PARTIAL
   drop only.
3. **This is a LOWER BOUND on nothing that matters.**  The quantity is a count
   and a maximum; both only grow as the file grows, which is why the freeze
   protocol is safe here but the freeze was still taken (see the header).
4. The capture's traffic is not a controlled variable -- it is whatever the
   boot-2 soak was doing.  See s3: the shape is traffic-dependent.
