# 155 — THE TX-SWEEP RACE: patch 810, AND THE CORRECTION TO DOC 154 §5.3

**Date:** 2026-09-21. Times are **AP `/proc/uptime` seconds** (the device RTC is unreliable).

**Status:** **the first AP-side driver fix in this series that was derived from a reproduced
byte-level fault and then verified in the built object before deployment.** Source changed in the
**tracked** tree only (`msm89xx/patches/810-bam-dmux-tx-sweep-race.patch`); the deployed
`/lib/modules/6.12.94/qcom_bam_dmux.ko` was replaced (previous build backed up to
`/overlay/modbackup/`).

---

## 1. Why this doc exists

Doc 154 identified a real fault — a NULL dereference at `bam_dmux_skb_dma_submit_tx+0x2c` reached
from `bam_dmux_tx_wakeup_work+0xc8` — but its **mechanism** was wrong. It claimed `state_lock`
does not protect against the sweep and that the in-tree comment at `qcom_bam_dmux.c:654` is false.

**Re-reading every call site shows the opposite**: the sweep is *always* under `state_lock`. The
hole is that `bam_dmux_netdev_start_xmit()` mutates the slot and the deferred bitmap *without* it.

This doc does three things:

1. **Corrects Doc 154 §5.3** with the verified lock discipline (§3).
2. **States the real race** — the sweep runs *first*, then `start_xmit` re-arms the bit (§4).
3. **Fixes it** in patch 810, proves the fix in the compiled object against the exact faulting
   instruction (§5–§6), and deploys and soaks it (§7–§8).

## 3. Correction: the sweep is always under `state_lock`

Doc 154 §5.3 asserted that neither `bam_dmux_power_off()` (`:1382`) nor `bam_dmux_pm_restart()`
(`:1607`) takes `state_lock`, so the `:654` comment was false. **Both halves are wrong.** Neither
function takes the lock *itself*, but **every caller holds it**:

| caller | call site | `state_lock` region |
| :-- | :-- | :-- |
| `bam_dmux_pc_irq()` — wake → `pm_restart()` | `:1715` | `:1701` … `:1737` |
| `bam_dmux_pc_irq()` — SSR recovery / teardown → `power_off()` | `:1709`, `:1732` | `:1701` … `:1737` |
| `bam_dmux_rx_watchdog_func()` — lost-edge resync → `pm_restart()` | `:1205` | `:1191` … `:1212` |
| `bam_dmux_power_on()` error paths → `power_off()` | `:1304`, `:1328`, `:1335` | inherited: `power_on()` is called at `:1707`, `:2067`, `:2215`, all under the lock |
| `bam_dmux_ssr_teardown()` → `power_off()` | `:1681` | inherited: called at `:2074`, `:2220`, and `:2293` (`mutex_lock` `:2292`) |

So `state_lock` **does** mutually exclude `tx_wakeup_work` from the sweep, the `:654` comment is
**substantially true**, and — importantly — that is exactly what makes the consumer-side fix in §5
race-free.

**Doc 154 §5.3, §5.4, §8 items 5–7 and §9 item 1 have been rewritten in place.** The fault decode
in Doc 154 §4 (which was byte-level and correct) is untouched.

## 4. The real race: the producer does not take the lock

`bam_dmux_netdev_start_xmit()` is `ndo_start_xmit` — **atomic context, so it cannot take the
mutex.** It takes only `tx_lock` inside `bam_dmux_tx_queue()` (`:356`) and sets the deferred bit at
`:599` with **no lock at all**:

```c
	if (active <= 0 || !READ_ONCE(dmux->pc_state)) {
		/* Cannot sleep here, or modem not awake yet: mark skb for wakeup handler and return */
		if (!atomic_long_fetch_or(BIT(skb_dma - dmux->tx_skbs),
					  &dmux->tx_deferred_skb)) {   /* <-- no lock */
			if (!READ_ONCE(dmux->in_teardown))
				queue_pm_work(&dmux->tx_wakeup_work);
		}
		...
	}
```

The winning interleaving is therefore the **reverse** of the one Doc 154 described — the sweep
clears the bitmap *before* `start_xmit` re-arms it, so "the bitmap was cleared" is not a guard:

| step | CPU A — `bam_dmux_netdev_start_xmit()` | CPU B — `bam_dmux_pc_irq()` (wake edge) |
| :-- | :-- | :-- |
| 1 | `bam_dmux_tx_queue()` → slot *i* now holds our skb (`:583`) | |
| 2 | `bam_dmux_skb_dma_map()` (`:594`) | |
| 3 | reads `pc_state` → **false** (still collapsed) ⇒ will take the defer branch (`:597`) | |
| 4 | | `state_lock` (`:1701`); `pc_state = true` (`:1704`); `pm_restart()` → `bam_dmux_free_skbs()` **NULLs slot *i*** and `atomic_long_set(&tx_deferred_skb, 0)` (`:1625`); unlock (`:1737`) |
| 5 | `atomic_long_fetch_or(BIT(i), …)` → **sets bit *i* on the now-empty bitmap** (`:599`); queues `tx_wakeup_work` (`:602`) | |
| 6 | | `tx_wakeup_work`: `pc_state` true, `pending = BIT(i)`, `skb_dma->skb == NULL` → **the crash** |

**Same shape as Doc 147's bug** — a slot reserved before a PM transition overtakes it — but on the
deferred-bitmap side instead of the map side.

The same race has three more reachable NULL sites, all in the same window:

* `bam_dmux_skb_dma_map()` (`:594`, `:471`) — dereferences `skb_dma->skb->data` at `0xc8`, which is
  **literally Doc 147's faulting load**;
* `bam_dmux_skb_dma_submit_tx()` from `start_xmit` (`:609`) — the same `skb->len` load as the
  observed crash;
* `bam_dmux_skb_dma_submit_tx()` from `send_cmd` (`:476`).

## 5. The fix — `msm89xx/patches/810-bam-dmux-tx-sweep-race.patch`

Four hunks, one file. The producer cannot be locked (atomic context), so **the consumers of a swept
slot are made tolerant** and the sweep's ownership is respected.

| # | function | change | why |
| :-- | :-- | :-- | :-- |
| 1 | `bam_dmux_skb_dma_map()` | `if (!skb_dma->skb) return false;` | covers `start_xmit` `:594` and `send_cmd` `:471` |
| 2 | `bam_dmux_skb_dma_submit_tx()` | `if (!skb_dma->skb) return false;` | covers the **observed** fault (`tx_wakeup_work`) and `start_xmit` `:609` |
| 3 | `bam_dmux_tx_wakeup_work()` loop | `if (!skb) { dev_dbg(...); continue; }` — **drop** the stale bit | a slot with no skb can never be submitted; restoring the bit instead would retry every 20 ms forever |
| 4 | `bam_dmux_netdev_start_xmit()` `drop:` | `if (READ_ONCE(skb_dma->skb) != skb) return NETDEV_TX_OK;` | the sweep already freed the skb and released its PM reference; `bam_dmux_tx_done()`+`dev_kfree_skb_any()` here would **double-free** and **double-put** |

Hunk 3 is the one that is **provably race-free**: the sweep NULLs slots under `state_lock` (§3) and
this loop reads them under `state_lock` (`:658`), so the test cannot be torn.

Hunk 4 is what makes hunks 1–2 safe to add. Without it, a guard returning `false` would route
`start_xmit` into a `drop:` path that frees an skb the sweep already freed.

### 5.1 The trap that was deliberately NOT taken

Doc 154 §9 item 1 suggested "optionally also `cancel_work_sync(&dmux->tx_wakeup_work)` in
`power_off()` / `pm_restart()`". **That would deadlock.** Both functions are called under
`state_lock` (§3) and `bam_dmux_tx_wakeup_work()` takes `state_lock` at `:658`, so
`cancel_work_sync()` would block forever waiting for a work item that is itself blocked on the lock
the canceller holds. The fix is tolerant-consumer, not cancel.

### 5.2 A related hazard that is *not* fixed

The RX path is unaffected: `bam_dmux_rx_slot_submit()` guarantees a non-NULL skb before mapping
(`:900-907`), so hunk 1 is a no-op there — verified, not assumed.

What remains is the **non-atomic** window itself. `start_xmit` can still free-path into the sweep
between any check and the following use; the guards shrink the exposure to "a check immediately
followed by the use", which cannot be made atomic without either taking `state_lock` in
`start_xmit` (impossible in atomic context) or moving the whole reserve+map+defer sequence under
`tx_lock` (a larger refactor that would hold a spinlock across `dma_map_single`). It is recorded as
open in §10.

## 6. The fix is visible in the compiled object, against the exact faulting instruction

Rebuilt with the OpenWrt toolchain
(`aarch64-openwrt-linux-musl-gcc-14.3.0`, `ARCH=arm64`, `make M=drivers/net/wwan modules`).
Crucially, **the module that actually crashed was recovered from the device backup**
(`/overlay/modbackup/qcom_bam_dmux.ko.prefix810`, md5 `3b693188c3ba27de9edeb7d1d1e53f76`,
227480 B) and disassembled — so the comparison below is against the real object, not a
reconstruction.

### 6.1 The crashing module reproduces BOTH oops addresses exactly

```
0000000000000b04 <bam_dmux_skb_dma_submit_tx>:
     b24:	a9400a95 	ldp	x21, x2, [x20]      ; x2 = skb_dma->skb  (offset 8)
     b2c:	f94036b3 	ldr	x19, [x21, #104]
     b30:	b9407056 	ldr	w22, [x2, #112]     ; <-- THE FAULTING INSTRUCTION
```

* `pc` — `b30 − b04` = **`0x2c`** → `bam_dmux_skb_dma_submit_tx+0x2c` — **exactly the oops `pc`**.
* `Code:` — `b9407056`, `ldr w22, [x2, #112]`, `#112` = `0x70` — **byte-for-byte the instruction
  the oops printed**, and `#112` is the BTF-verified `skb->len` offset.
* `lr` — `bam_dmux_tx_wakeup_work` starts at `12e8` and the `bl` is at `13ac`; on arm64 `bl` sets
  `x30` to the **next** instruction, so `lr = 13b0 − 12e8` = **`0xc8`** →
  `bam_dmux_tx_wakeup_work+0xc8` — **exactly the oops `lr`**.

```
    13a8:	8b000260 	add	x0, x19, x0
    13ac:	97fffdd6 	bl	b04 <bam_dmux_skb_dma_submit_tx>
```

So the entire Doc 154 §4 decode — `x2 = skb_dma->skb`, offset `0x70` = `skb->len`, reached from the
`tx_wakeup_work` loop — is confirmed by disassembling the object that faulted, independently of the
register dump.

### 6.2 The fixed build puts the guard immediately before it

```
0000000000000b10 <bam_dmux_skb_dma_submit_tx>:
     b10:	f9400402 	ldr	x2, [x0, #8]        ; x2 = skb_dma->skb
     b14:	b40005a2 	cbz	x2, bc8             ; <-- HUNK 2: the new guard
     ...
     b44:	b9407056 	ldr	w22, [x2, #112]    ; skb->len (112 = 0x70)
```

`ldr w22, [x2, #112]` is now at `+0x34` (the guard cost 8 bytes in this function), and the `cbz x2`
that branches to the error path sits 0x30 bytes ahead of it. There is no path from function entry
to the `skb->len` load that does not pass the test.

Loop-body guard (hunk 3) in `bam_dmux_tx_wakeup_work`:

```
    13d0:	8b000260 	add	x0, x19, x0         ; x0 = skb_dma
    13d4:	b4000081 	cbz	x1, 13e4            ; <-- HUNK 3: if (!skb) goto continue
    13d8:	97fffdce 	bl	b10 <bam_dmux_skb_dma_submit_tx>
```

`13e4` is the loop-continue point, so a NULL slot skips the submit and the bit is dropped.

### 6.3 The build is reproducible

The fixed source rebuilds to the **identical** md5 `395cb590a24418e317048c2e21fb5fbe` on a second
run, and `diff` confirms the in-tree source equals the saved fixed source. The only compiler output
is the harmless `environment variable 'STAGING_DIR' not defined` warning from the wrapper.

## 8. Soak

The oops appeared in a boot with heavy A2 power-collapse activity
(`pc_vote_tx_count: 186`, `pm_suspend_attempts: 185`). The soak must therefore **keep the modem
collapsing**, which turns out to be the non-obvious part.

### 8.1 Phase 1 (FAILED to exercise the path) — continuous 1 Hz ping

`pc_irq_count`, `pc_vote_tx_count` and `pm_suspend_attempts` all **froze at 29 / 15 / 14 and did not
move for 105 s**. Continuous traffic holds the modem permanently awake, so it never collapses, the
`start_xmit` defer branch at `:597` is never taken, and the race window never opens. **A 1 Hz ping
soak does not test this bug at all.** (Data kept as `/overlay/soak810_phase1_1hz.csv`.)

### 8.2 Phase 2 (the real test) — idle-then-burst

The race needs *both* a collapsed modem (so `start_xmit` defers) **and** a wake edge landing in the
window. So the harness now idles 20 s to let the modem collapse, then fires 8 packets at 0.2 s
intervals, forever — repeatedly colliding TX with the wake transition.

Measured, immediately after the change:

| uptime | pc_irq | pc_vote | pm_susp | pc_state |
| :-- | :-- | :-- | :-- | :-- |
| 293.31 s | 29 | 15 | 15 | 1 |
| 384.05 s | 38 | 19 | 19 | 0 |
| 434.46 s | **46** | **23** | **23** | 0 |

**23 collapse/wake cycles in ~140 s** (vs 0 in phase 1), the bearer still up
(`wwan0` = `10.132.105.60/29`, `ping 8.8.8.8` → 3/4), and

```
oops = 0    fatal = 0
```

> **SOAK RESULT: in progress at the time of writing — 23 collapse cycles and 0 oopses.** The final
> count is recorded in `/overlay/soak810.csv` on the device and in §9. Note this is a **negative
> result so far, not a proof**: the oops occurred **once in ~1170 s** with ~185 cycles on the
> crashing build, so a clean run of a few hundred cycles is consistent with the fix working *and*
> with the race simply not having fired yet.

## 9. Established vs not established

**Established (measured / source-verified):**

1. **Doc 154 §5.3 was wrong**: every call to `bam_dmux_power_off()` and `bam_dmux_pm_restart()` is
   made with `state_lock` held; the `:654` comment is substantially true (§3).
2. The hole is the **producer**: `bam_dmux_netdev_start_xmit()` sets `tx_deferred_skb` at `:599`
   without `state_lock`, so it can re-arm a bit for a slot a concurrent sweep already freed (§4).
3. The race is reachable at four NULL sites, including Doc 147's own `skb->data` load (§4).
4. **`cancel_work_sync(&tx_wakeup_work)` in `power_off()`/`pm_restart()` would deadlock** (§5.1).
5. Patch 810 applies cleanly, builds without warnings, and **the pre-fix build reproduces both
   reported addresses exactly** — `pc` `b30 − b04 = 0x2c` and `lr` `13b0 − 12e8 = 0xc8`, with the
   faulting word `b9407056` (`ldr w22, [x2, #112]`) — and the fixed build places `cbz x2`
   immediately ahead of that same instruction (§6). The fixed source rebuilds to an identical md5.
6. The fixed module is deployed and the link is healthy with **0 oopses** (§7).

**Not established:**

* Whether the race is what actually fired on 2026-09-21 — §4's table is the only interleaving
  consistent with every fact, not an observed trace.
* Whether the fix *prevents* the oops under soak (§8, pending).
* Whether the same race explains the **failed modem restart** after fatal #15 (Doc 154 §6) — still
  separate and unexplained.
* The residual non-atomic window in `start_xmit` (§5.2).

## 12. One line

Doc 154's mechanism was wrong — the sweep is *always* under `state_lock`; the real defect is that
`bam_dmux_netdev_start_xmit()` re-arms `tx_deferred_skb` **without** it, after a concurrent
`bam_dmux_free_skbs()` sweep has already freed the slot — and **patch 810** fixes it by making the
consumers tolerant (drop NULL-slot bits, NULL-guard the two DMA helpers, and stop `start_xmit`'s
`drop:` from double-freeing what the sweep already owns), a change proven in the built object by
reproducing both oops addresses (`+0x2c`, `+0xc8`) and showing the new `cbz` immediately before the
faulting `ldr w22, [x2, #112]`.
